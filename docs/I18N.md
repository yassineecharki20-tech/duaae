# DUAA — Internationalization (ar · fr · en)

The app ships in three languages. **Arabic is the default** for anyone without a stored preference,
and it is the source of truth for the catalog: every other language is type-checked against it.

| | Arabic | French | English |
|---|---|---|---|
| Code | `ar` | `fr` | `en` |
| Direction | RTL | LTR | LTR |
| BCP-47 tag (`localeTagFor`) | `ar` | `fr` | `en` |
| Catalog | `src/core/i18n/messages/ar.ts` | `…/fr.ts` | `…/en.ts` |
| Top-level keys | **842** | **804** | **804** |

Arabic has 38 more keys than French/English because it carries CLDR plural sub-keys
(`zero`, `one`, `two`, `few`, `many`) that Latin languages do not need — see §4. The parity test
enforces that this is the *only* allowed difference.

---

## 1. Layout

```
src/core/i18n/
├── messages/
│   ├── ar.ts          source catalog; exports `MessageCatalog`, `MessageKey`, `AnyMessageKey`
│   ├── fr.ts          typed `MessageCatalog` — a missing/renamed key fails `tsc`
│   └── en.ts          typed `MessageCatalog`
├── state.ts           runtime: active language, translate/translatePlural, direction, locale
├── plurals.ts         CLDR plural selection per language
├── rtl.ts             platform side-effects (document dir/lang, I18nManager)
├── options.ts         localized option lists — *functions of* `t`
├── I18nProvider.tsx   React binding: `useI18n()`, `useT()`, `useTp()`
└── index.ts           public barrel
```

`state.ts` and `plurals.ts` are **pure modules** (no React, no react-native) so services, `AppError`
construction and Node-side tests can use them. `rtl.ts` holds the platform split; `index.ts` pulls in
React, so logic code deep-imports `@/core/i18n/state`.

## 2. Using it

**Inside a component** — always `useI18n()`. It re-renders the subtree when the language changes:

```tsx
const { t, tp, isRTL, language, locale } = useI18n();

<AppText>{t('home.greeting.morning')}</AppText>
<AppText>{tp('favorites.collectionCount', collections.length)}</AppText>
<AppText>{t('favorites.collectionCreated', { name: saved })}</AppText>
```

**Outside React** (services, errors, share payloads, notifications) — the module functions read the
same active language:

```ts
import { translate, translatePlural } from '@/core/i18n/state';
AppError.validation({ code: 'FAVORITES_DUPLICATE_NAME', userMessage: translate('favorites.error.duplicate') });
```

**Key safety.** `t()` only accepts `MessageKey` — the union of `ar.ts`'s literal keys — so a typo or a
deleted key is a compile error, never a raw key on screen. Keys with plural forms accept the count
through `tp()`; `translatePlural(key, count, params, language?)` picks the sub-key.

**Option lists must be built during render.** A module-level array of labels freezes the language at
import time, so `src/core/i18n/options.ts` exports *builders*: `appearanceOptions(t)`,
`paletteOptions(t)`, `accentOptions(t)`, `fontProfileOptions(t)`, `textSizeOptions(t)`,
`densityOptions(t)`, `cardStyleOptions(t)`, `languageOptions(t)`, `motionOptions(t)`,
`widgetContentOptions(t)`, `homeSectionOptions(t)`, `homeSectionLabel(t, id)`. Screens call them inside
`useMemo(… , [t])`.

## 3. Direction (RTL ⇄ LTR)

* `directionFor(language)` → `'rtl'` for `ar`, `'ltr'` for `fr`/`en`. The direction is **derived from
  the language**, never stored twice.
* `bootRTL()` runs at module scope in `src/app/_layout.tsx` before the first paint. It deliberately
  does *not* force RTL: it only allows it, so an existing French/English preference is respected.
* **Web:** `applyDocumentLocale()` sets `dir` and `lang` on `<html>` and pushes the locale into
  react-native-web's `LocaleProvider`, so the flip is instant — no reload, no restart.
* **Native:** `applyLanguagePreference()` calls `I18nManager.forceRTL()` when the direction actually
  differs and returns `true`; the store records `restartNeededForDirection` and
  Settings ▸ Language renders an honest card explaining that reopening the app applies the new
  direction (with an acknowledge button). Text direction inside components still flips immediately.
* `src/app/+html.tsx` ships `<html lang="ar" dir="rtl">` and interpolates its shell colours from the
  design tokens, so the very first static paint matches the themed app.

## 4. Plurals

CLDR categories, selected by `pluralForm(language, count)`:

| Language | Rule |
|---|---|
| Arabic | `zero` 0 · `one` 1 · `two` 2 · `few` 3–10 (n mod 100 = 3..10) · `many` 11–99 · `other` |
| French | `one` for 0 and 1 · `other` |
| English | `one` for 1 · `other` |

A plural key is stored as the base key plus dotted sub-keys, with the base holding `other`:

```ts
'favorites.countSummary': '{count} من الأدعية محفوظة',      // other
'favorites.countSummary.zero': 'لا أدعية محفوظة بعد',
'favorites.countSummary.one': 'دعاء واحد محفوظ',
'favorites.countSummary.two': 'دعاءان محفوظان',
'favorites.countSummary.few': '{count} أدعية محفوظة',
'favorites.countSummary.many': '{count} دعاءً محفوظًا',
```

Latin catalogs only need the base (`other`) and, where the language distinguishes it, `.one`. The
parity test allows Arabic to have *extra* plural sub-keys and requires that `{placeholder}` names match
across languages — with one deliberate exemption for `{count}`, because Arabic spells small numbers out
in words and may not use the placeholder at all.

## 5. Content policy for translations

* **Religious text is never translated.** Duas, adhkar and Qur'anic verses stay in Arabic in every
  language: no fabricated translations, no paraphrase presented as scripture. What is translated is the
  UI chrome around them — headings, buttons, empty states, errors, accessibility labels, dates.
* The language screen states this explicitly (`settings.language.scriptureNote`), so a French user is
  told why the text itself remains Arabic.
* Arabic characters appear in the French and English catalogs in exactly **7 allowlisted keys** (brand
  name, the calligraphic wordmark, a dhikr example, the Arabic font/reading preview, and the native
  name of the Arabic language). `tests/i18n.test.ts` fails if an eighth one appears.

## 6. Persistence and switching

* The language lives in the single preferences object: `useSettingsStore().preferences.language`
  (`src/core/types/domain.ts` → `AppPreferences`), persisted under `duaa:v1:settings`.
* On boot the store rehydrates, calls `setActiveLanguage()` and `applyLanguagePreference()`. With no
  stored value the default is Arabic.
* `setLanguage()` returns `boolean` = "needs a restart for direction" (native only). It updates the
  runtime immediately, so the whole tree re-renders in the new language with no reload
  (`tests/app/personalization.test.tsx` asserts exactly this: home renders in French, `document.dir`
  flips to `ltr`, and the choice is persisted).

## 7. Enforcement (tests)

| Test | What it guards |
|---|---|
| `tests/i18n.test.ts` | Catalog parity (same key set modulo plural sub-keys), no Arabic leaking into fr/en outside the 7-key allowlist, placeholder parity, plural selection for all three languages, `directionFor`/`localeTagFor`, option builders return every value with a non-empty label |
| `tests/no-hardcoded-strings.test.ts` | A lexer scans every `src/**/*.{ts,tsx}` file and fails on user-facing literals: Arabic characters outside the i18n catalogs, quoted strings in JSX text position, and `Record<AppLanguage, string>` label maps outside `core/i18n`. Religious text in `﴿ ﴾` and the content corpus are exempt |
| `tests/app/personalization.test.tsx` | Language switch re-renders without restart, DOM `dir`/`lang` flip, persistence, and the Settings ▸ Language row working end to end |

## 8. Adding a fourth language

1. Add the code to `APP_LANGUAGES` in `src/core/types/domain.ts` (and to `RTL_LANGUAGES` /
   `LOCALE_TAGS` in `core/i18n/state.ts` if it is RTL or needs a region tag).
2. Create `src/core/i18n/messages/<lang>.ts` typed `MessageCatalog` — `tsc` lists every missing key.
3. Register it in `CATALOGS` (`state.ts`) and add its plural rule in `plurals.ts` if it is not
   `one`/`other`.
4. Add a native-name key (`settings.language.native.<lang>`) and a row in `languageOptions()`; the
   language screen renders rows from that builder, so no screen change is needed.
5. Run `npm test` — the parity and no-hardcoded-strings suites will catch anything missed.
